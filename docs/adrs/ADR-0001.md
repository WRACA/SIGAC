# ADR-0001 — Adoptar React, Tailwind CSS, Rust, Axum y PostgreSQL para SIGAC

**Status:** Accepted  
**Fecha:** 29/09/2026  
**Relacionado con:** [ADR-0000 — Replantear la arquitectura y el stack tecnológico del proyecto](./ADR-0000.md)  
**Discusión previa:** [RFC-0000 — Selección del stack tecnológico para SIGAC](../rfcs/RFC-0000.md)

## Contexto

Después de reabrir la discusión sobre la arquitectura y el stack tecnológico de SIGAC mediante [ADR-0000](./ADR-0000.md), se evaluaron diferentes alternativas para frontend, backend y persistencia en [RFC-0000](../rfcs/RFC-0000.md).

La arquitectura acordada mantiene una separación explícita entre frontend y backend. El frontend funcionará como cliente de una API independiente, mientras que la lógica de negocio, autenticación, autorización, validaciones y acceso a datos permanecerán en el backend.

La aplicación web se desarrollará siguiendo un enfoque **mobile-first**, considerando principalmente el uso desde dispositivos móviles para procesos como el pase de lista mediante código QR, pero manteniendo compatibilidad con tablet y escritorio.

Aunque una aplicación móvil nativa no forma parte del alcance actual, la separación entre frontend y backend permitirá incorporar en el futuro otros clientes sin reemplazar la lógica de negocio existente.

## Decisión

Se adopta el siguiente stack tecnológico para SIGAC:

| Capa | Tecnología |
|---|---|
| Lenguaje frontend | TypeScript |
| Frontend | React |
| Estilos | Tailwind CSS |
| Lenguaje backend | Rust |
| Framework backend | Axum |
| Runtime asíncrono | Tokio |
| Base de datos | PostgreSQL |
| Proveedor PostgreSQL | Neon |
| Comunicación frontend/backend | API REST sobre HTTPS |
| Formato de intercambio | JSON |

La arquitectura general será:

```text
                    SIGAC

            +------------------+
            |      React       |
            |    TypeScript    |
            |   Tailwind CSS   |
            |   Mobile-first   |
            +--------+---------+
                     |
                     | HTTPS
                     | REST / JSON
                     v
            +--------+---------+
            |      Axum        |
            |      Rust        |
            |      Tokio       |
            +--------+---------+
                     |
                     |
                     v
            +--------+---------+
            |   PostgreSQL     |
            |      Neon        |
            +------------------+
```

Frontend y backend serán aplicaciones independientes, aunque podrán mantenerse dentro del mismo repositorio.

## Frontend

El frontend será desarrollado utilizando **React con TypeScript**.

React será responsable exclusivamente de la interfaz y de la interacción del usuario con SIGAC. No deberá contener reglas de negocio críticas cuya validación corresponda al servidor.

**Tailwind CSS** será utilizado como sistema principal de estilos.

La interfaz seguirá una estrategia **mobile-first**:

```text
Móvil
  ↓
Tablet
  ↓
Escritorio
```

Los componentes se diseñarán inicialmente para pantallas pequeñas y posteriormente se ampliarán mediante los breakpoints correspondientes.

Entre las responsabilidades del frontend se encuentran:

- renderizar la interfaz;
- gestionar formularios;
- consumir la API;
- administrar estado de interfaz;
- mostrar errores y resultados provenientes del backend;
- acceder a la cámara del dispositivo para lectura de códigos QR;
- mostrar dashboards, tablas y gráficas;
- adaptar la interfaz según el rol del usuario.

El frontend no será responsable de decidir si una operación de negocio es válida.

Por ejemplo:

```text
Frontend
   |
   | token QR
   v
Backend
   |
   ├── validar usuario
   ├── validar rol
   ├── validar sesión
   ├── validar socio
   ├── validar membresía
   ├── validar inscripción
   ├── comprobar duplicado
   └── registrar asistencia
```

## Backend

El backend será desarrollado utilizando **Rust** con **Axum** como framework HTTP.

Se utilizará **Tokio** como runtime asíncrono.

El backend mantendrá la lógica de negocio y será responsable de:

- autenticación;
- autorización y control de acceso por roles;
- gestión de usuarios;
- gestión de socios e instructores;
- actividades y horarios;
- inscripciones;
- sesiones;
- validación y registro de asistencias;
- membresías;
- pagos;
- generación de datos para dashboards;
- validación de reglas de negocio;
- acceso a PostgreSQL.

El backend se implementará inicialmente como un **monolito modular**.

Una posible organización por dominio será:

```text
backend/
└── src/
    ├── auth/
    ├── users/
    ├── members/
    ├── instructors/
    ├── activities/
    ├── schedules/
    ├── enrollments/
    ├── sessions/
    ├── attendance/
    ├── memberships/
    ├── payments/
    ├── dashboard/
    └── main.rs
```

Estos módulos no representan microservicios independientes.

Todos formarán parte de una única aplicación backend.

## Base de datos

Se utilizará **PostgreSQL** como sistema gestor de base de datos relacional.

La instancia desplegada del proyecto utilizará **Neon** como proveedor administrado de PostgreSQL.

La selección de PostgreSQL se mantiene debido a la naturaleza fuertemente relacional del dominio de SIGAC y a la necesidad de garantizar integridad mediante:

- claves primarias;
- claves foráneas;
- restricciones `UNIQUE`;
- transacciones;
- restricciones de integridad;
- relaciones entre socios, actividades, sesiones, membresías, pagos y asistencias.

Neon será utilizado como infraestructura para PostgreSQL, pero el sistema deberá evitar depender innecesariamente de funcionalidades propietarias del proveedor.

La aplicación deberá trabajar contra PostgreSQL estándar de manera que sea posible utilizar otro proveedor o una instancia local en caso de ser necesario.

```text
Desarrollo local
PostgreSQL
     |
     | mismo esquema
     v
Producción / piloto
PostgreSQL en Neon
```

## Comunicación entre frontend y backend

La comunicación entre React y Axum se realizará mediante una API REST utilizando HTTPS y JSON.

Ejemplo:

```text
React
  |
  | POST /api/sessions/{id}/attendance
  |
  v
Axum
  |
  v
PostgreSQL
```

La API deberá constituir el contrato entre clientes y backend.

Esta separación permitirá que en el futuro otro cliente pueda consumir la misma API:

```text
                    +-------------+
                    | React Web   |
                    +------+------+
                           |
                           |
+------------------+       |
| Aplicación móvil |-------+
| futura           |       |
+------------------+       |
                           v
                      +----+----+
                      |  Axum   |
                      |  API    |
                      +----+----+
                           |
                           v
                      PostgreSQL
```

## Alternativas consideradas

Durante la discusión se consideraron distintas tecnologías, entre ellas:

### Frontend

- React;
- Next.js;
- Vue;
- Nuxt;
- SvelteKit;
- Angular;
- Flutter Web.

### Backend

- FastAPI;
- Django REST Framework;
- Spring Boot;
- NestJS;
- Go;
- Rust con Axum.

### Persistencia

Se consideraron diferentes formas de acceso y despliegue de PostgreSQL, manteniéndose finalmente PostgreSQL como motor y Neon como proveedor administrado.

La comparación detallada de las alternativas se encuentra en [RFC-0000](../rfcs/RFC-0000.md).

## Consecuencias

### Positivas

- Frontend y backend quedan claramente separados.
- La lógica de negocio no depende de React.
- El backend puede ser reutilizado por una futura aplicación móvil.
- Rust proporciona tipado estático fuerte y seguridad de memoria.
- Axum permite construir una API ligera y modular.
- El backend puede operar con un consumo reducido de recursos.
- React dispone de un ecosistema amplio para interfaces administrativas.
- Tailwind facilita el desarrollo mobile-first y responsivo.
- PostgreSQL proporciona las garantías de integridad necesarias para el dominio.
- Neon permite utilizar PostgreSQL administrado sin modificar el modelo relacional.
- El sistema no queda ligado a una aplicación móvil, framework móvil o cliente específico.
- El monolito modular mantiene la arquitectura sencilla durante el MVP.

### Negativas

- El equipo deberá trabajar con dos lenguajes principales: TypeScript y Rust.
- Rust presenta una curva de aprendizaje mayor que otras alternativas evaluadas.
- El desarrollo inicial del backend puede ser más lento que con FastAPI, Django o NestJS.
- Algunas funcionalidades comunes, como autenticación y autorización, requerirán mayor configuración que en frameworks más integrales.
- Frontend y backend requerirán procesos independientes de ejecución, testing y deployment.
- Será necesario mantener explícitamente el contrato de la API.
- El uso de Neon agrega una dependencia de infraestructura externa, aunque PostgreSQL permite cambiar de proveedor posteriormente.

## Consecuencias para el repositorio

El repositorio deberá separar físicamente ambas aplicaciones.

Una estructura inicial propuesta es:

```text
SIGAC/
│
├── frontend/
│   ├── src/
│   ├── public/
│   ├── tests/
│   └── ...
│
├── backend/
│   ├── src/
│   ├── tests/
│   ├── migrations/
│   └── ...
│
├── docs/
│   ├── decisiones/
│   │   ├── ADR-0000.md
│   │   └── ADR-0001.md
│   │
│   └── rfcs/
│       └── RFC-0000.md
│
├── .gitignore
├── DEFINICION.md
└── README.md
```

El hecho de utilizar un único repositorio no significa que frontend y backend constituyan una sola aplicación.

Ambas partes deberán poder ejecutarse, probarse y desplegarse independientemente.

## Decisiones pendientes

Este ADR define las tecnologías principales, pero no resuelve automáticamente todas las decisiones de implementación.

Quedan pendientes, entre otras:

- librería o estrategia concreta para acceso a PostgreSQL desde Rust;
- sistema de migraciones;
- estrategia de autenticación;
- cookies de sesión frente a access/refresh tokens;
- estructura definitiva de endpoints REST;
- librería para lectura de QR en React;
- estrategia de manejo de estado y fetching en frontend;
- librería de componentes sobre React/Tailwind, en caso de utilizarse;
- estrategia de testing;
- Docker y entorno de desarrollo local;
- deployment del frontend;
- deployment del backend;
- CI/CD.

Cuando alguna de estas decisiones tenga impacto arquitectónico suficiente deberá documentarse mediante su correspondiente ADR o RFC.
