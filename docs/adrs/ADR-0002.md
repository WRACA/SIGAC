# Usar `qrcode.react` para generar los códigos QR en el frontend

**Status:** Aceptado

**Fecha:** 2026-11-12

**Historias relacionadas:** SIG-95 (generación de credenciales QR), SIG-96 (visualización del QR personal del socio)

## Contexto

Cada socio de SIGAC tiene una credencial QR (tabla `credencial_qr`). El backend genera y valida el token, y devuelve el contenido del QR con el formato estándar:

```text
SIGAC:SOCIO:1:<UUID>
```

El endpoint `GET /api/socio/credencial-qr` entrega solo esa cadena. El frontend (React 19 + Vite + Tailwind) tiene que **dibujarla** como código QR en el perfil del socio, para presentarla en recepción (inscripciones) y en las clases (pase de lista).

Requisitos de la generación visual (SIG-96):

- Generar un QR legible a partir de una cadena de texto.
- Que el QR pueda escanearse desde otro dispositivo con un lector compatible.
- Que el componente pueda reutilizarse en otras vistas.
- Que el diseño respete la paleta de colores del sistema (tema oscuro, acento naranja).
- Que se vea nítido en celulares, porque el diseño es mobile-first (ver ADR-0000).

La **generación** del QR (dibujarlo) es un problema distinto del **escaneo** (leerlo con la cámara). El RFC-0000 menciona ZXing / html5-qrcode para el escaneo; este ADR solo trata la generación.

---

## Decisión

Se usa la librería **[`qrcode.react`](https://github.com/zpao/qrcode.react)** (versión `^4.2.0`), con su componente **`QRCodeSVG`**.

Se encapsula en el componente reutilizable `frontend/src/components/CodigoQR.jsx`:

```jsx
<CodigoQR valor="SIGAC:SOCIO:1:<UUID>" />
```

Configuración fija dentro del componente:

| Parámetro | Valor | Motivo |
|---|---|---|
| Renderizado | SVG (`QRCodeSVG`) | Nítido a cualquier tamaño y densidad de pantalla |
| Corrección de errores | `level="M"` (~15 %) | Equilibrio entre densidad y tolerancia a reflejos o brillo de pantalla |
| Zona de silencio | `marginSize={4}` | Margen de 4 módulos que exige el estándar QR para que la cámara lo detecte |
| Colores | `fgColor` / `bgColor` desde una paleta | Integración con la identidad visual |

### Paletas de color

Los colores salen de un catálogo en `frontend/src/utils/paletasQR.js`. **La paleta la elige el equipo de desarrollo, no el usuario**, con la constante:

```js
export const PALETA_QR_POR_DEFECTO = "clasica";
```

Reglas que debe cumplir cualquier paleta para que el QR siga siendo escaneable:

- Módulos **oscuros** sobre fondo **claro**, porque muchos lectores no leen QR invertidos.
- Contraste WCAG **≥ 7:1** entre módulos y fondo.
- El naranja de la marca (`#ff5a00`) sobre blanco da solo ~3.1:1, así que se usa en el **marco** del componente y no en los módulos.

## Alternativas consideradas

### Alternativa A: `qrcode` (node-qrcode)

| Aspecto | Consideración |
|---|---|
| Integración con React | No nativa: genera canvas o data URL de forma imperativa |
| Uso en componentes | Requiere `useEffect` / `ref` y manejar el ciclo de vida a mano |
| Personalización de colores | Sí |
| Tamaño | Mayor que `qrcode.react` |

Es válida, pero obliga a escribir un envoltorio React que `qrcode.react` ya resuelve.

### Alternativa B: `react-qr-code`

| Aspecto | Consideración |
|---|---|
| Integración con React | Nativa (SVG) |
| Personalización de colores | Sí |
| Opciones adicionales | Menos (sin imagen central con hueco, sin canvas) |
| Adopción | Menor que `qrcode.react` |

Funcionalmente parecida, pero con menos opciones y menos uso en la comunidad.

### Alternativa C: `qr-code-styling`

| Aspecto | Consideración |
|---|---|
| Personalización | Muy alta (módulos redondeados, degradados, logotipos) |
| Integración con React | No nativa (API imperativa) |
| Riesgo | Los estilos agresivos pueden reducir la legibilidad para la cámara |
| Tamaño | Mayor |

La personalización extra no es un requisito, y aumenta el riesgo de generar QR difíciles de escanear.

### Alternativa D: generar la imagen del QR en el backend

| Aspecto | Consideración |
|---|---|
| Contrato de API | El endpoint devolvería una imagen (PNG/SVG) en lugar de texto |
| Estilo visual | Quedaría acoplado al backend |
| Reutilización | Un cliente móvil futuro recibiría una imagen ya estilizada |

Contradice la separación del ADR-0000: la presentación es responsabilidad del frontend. Además, devolver solo la cadena permite que cada cliente (web o móvil futuro) dibuje el QR con su propia tecnología.

## Consecuencias

### Positivas

- Componente React declarativo: el QR se actualiza al cambiar `valor` o la paleta, sin código imperativo.
- **Sin dependencias de ejecución**: solo tiene `react` como *peer dependency* (compatible con React 16.8 a 19).
- Licencia **ISC**, permisiva y compatible con el proyecto.
- El SVG escala sin perder nitidez en pantallas de alta densidad.
- Los colores son configurables, lo que permite seguir la identidad visual sin sacrificar la legibilidad.
- El componente `CodigoQR` aísla la librería: si en el futuro se reemplaza, solo cambia ese archivo.
- El backend sigue entregando solo texto, así que el contrato de API no depende de la librería.

### Negativas

- Se agrega una dependencia más al frontend que hay que mantener actualizada.
- Personalización limitada: no permite colorear los patrones de esquina por separado ni usar degradados nativos.
- Cualquier cambio de paleta debe respetar las reglas de contraste. Si no, el QR podría dejar de leerse en algunos dispositivos.
- La librería no resuelve el **escaneo**. Eso queda pendiente de una decisión aparte (ver RFC-0000: ZXing / html5-qrcode).
