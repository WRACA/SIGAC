# Usar `barcode-detector` (BarcodeDetector nativo + ponyfill ZXing WASM) para escanear códigos QR en el frontend

**Status:** Aceptado

**Fecha:** 2026-11-18

**Historias relacionadas:** SIG-97 (inscripción de socios mediante QR desde recepción)

## Contexto

La credencial de cada socio es un QR con el contenido:

```text
SIGAC:SOCIO:1:<UUID>
```

ADR-0001 resolvió cómo **dibujar** ese QR (`qrcode.react`) y dejó pendiente cómo **leerlo**. En SIG-97, el recepcionista inscribe socios a una sesión escaneando su credencial con la cámara de **su propio dispositivo** (BYOD). El texto leído se envía a:

```text
POST /api/recepcionista/sesiones/{sesion_id}/inscripciones/qr   { "contenido": "<texto del QR>" }
```

Requisitos del escaneo:

- Lectura en tiempo real desde el navegador móvil, sin instalar aplicaciones (RFC-0000: "Escaneo QR desde navegador móvil", obligatorio).
- Funcionar en Android (Chrome) y en iOS (Safari), porque el dispositivo lo pone el recepcionista.
- Lectura rápida (RNF-01: escaneo en menos de 3 s).
- Control total de la interfaz, para respetar el diseño mobile-first (ADR-0000) y la paleta del sistema.
- Control del ciclo de vida de la cámara: encenderla y apagarla al desplegar o colapsar el lector, y apagarla tras cada lectura para no procesar dos veces la misma credencial.

Como referencia se revisó la solución de otro proyecto (`docs/QR/SOLUCION-QR.md`). Esa solución usa `getUserMedia` + `BarcodeDetector` nativo, con `jsqr` como respaldo, y recomienda sustituir `jsqr` por el polyfill `barcode-detector`.

---

## Decisión

Se usa la librería **[`barcode-detector`](https://github.com/Sec-ant/barcode-detector)** (versión `^3.2.4`), que implementa la API estándar `BarcodeDetector` sobre **ZXing-C++ compilado a WebAssembly** (`zxing-wasm`).

Estrategia:

1. Si el navegador tiene `BarcodeDetector` nativo con soporte para `qr_code` (Chrome/Edge en Android y escritorio), se usa el nativo.
2. Si no (Safari/iOS, Firefox), se carga de forma **diferida** el ponyfill: `import("barcode-detector/ponyfill")`. No se modifica `window` y la librería no pesa en el bundle inicial.
3. En ambos casos el código es el mismo: `new BarcodeDetector({ formats: ["qr_code"] })` y `detector.detect(video)`.

La cámara se maneja con la API nativa `navigator.mediaDevices.getUserMedia` (cámara trasera: `facingMode: { ideal: "environment" }`) y un `<video playsInline muted>`.

Todo queda encapsulado en el componente reutilizable `frontend/src/components/EscanerQR.jsx`:

```jsx
<EscanerQR onLectura={(contenido) => { /* ... */ }} />
```

| Comportamiento | Detalle |
|---|---|
| Encendido | La cámara se enciende al **montar** el componente |
| Apagado | Al **desmontarlo** se detienen todas las pistas (`track.stop()`) |
| Bucle de lectura | Analiza un cuadro cada ~300 ms; los errores por cuadro se ignoran |
| Lectura única | Al detectar el primer QR apaga la cámara y llama **una sola vez** a `onLectura` |
| Errores | Mensajes claros para contexto no seguro (sin HTTPS), permiso denegado, sin cámara o cámara ocupada |

El componente no conoce el formato del QR ni el endpoint: solo entrega el texto. La validación del contenido la hace el backend (`backend/src/qr.rs`).

## Alternativas consideradas

### Alternativa A: `BarcodeDetector` nativo + `jsqr` (la solución de SGA-QR)

| Aspecto | Consideración |
|---|---|
| Dependencias | Ligera (`jsqr`) |
| Código | Dos ramas distintas: `detect()` nativo y `jsQR(imageData)` sobre un canvas |
| Rendimiento en iOS | `jsqr` es JavaScript puro, más lento en gama baja |
| Mantenimiento | `jsqr` tiene poca actividad |

Funciona, pero obliga a mantener dos caminos de código, y el respaldo es el más lento justamente en iOS.

### Alternativa B: `html5-qrcode` (sugerida en RFC-0000)

| Aspecto | Consideración |
|---|---|
| API | De alto nivel: maneja la cámara, la selección de dispositivo y la lectura desde archivo |
| Interfaz | Inyecta su propio DOM y estilos; cuesta adaptarlo al diseño |
| Mantenimiento | Irregular |
| Tamaño | Mayor |

Resta control sobre la interfaz y sobre el ciclo de vida de la cámara, que en esta historia es un requisito explícito (apagar la cámara al colapsar el lector).

### Alternativa C: `@zxing/browser` (sugerida en RFC-0000)

| Aspecto | Consideración |
|---|---|
| Motor | Port de ZXing a JavaScript, robusto y multiformato |
| API | `decodeFromVideoDevice()` con callback continuo |
| Rendimiento | Inferior al de ZXing-C++ en WASM |
| Tamaño | Relativamente grande y siempre presente, aunque el navegador tenga lector nativo |

### Alternativa D: `qr-scanner` (nimiq)

| Aspecto | Consideración |
|---|---|
| Rendimiento | Muy bueno (nativo o Web Worker), ~16 kB gzip |
| API | Propia, no estándar |

Es una buena opción, pero la API propia acopla el código a la librería. Con `barcode-detector`, el día que todos los navegadores soporten `BarcodeDetector` basta con eliminar el ponyfill.

### Alternativa E: `@yudiel/react-qr-scanner`

| Aspecto | Consideración |
|---|---|
| Integración | Componente React listo (`<Scanner onScan />`) construido sobre `barcode-detector` |
| Control | Menor control de la interfaz y del ciclo de vida de la cámara |

Usa el mismo motor elegido, pero añade una capa que no aporta y quita control.

## Consecuencias

### Positivas

- **Una sola API** (la estándar `BarcodeDetector`) en todos los navegadores, sin ramas condicionales de decodificación.
- En Chrome/Android se usa el lector **nativo**, sin descargar nada extra.
- En Safari/iOS, ZXing-C++ en WASM ofrece buen rendimiento y robustez.
- Carga **diferida**: el ponyfill solo se descarga si el navegador no tiene soporte nativo.
- Control total de la interfaz y de la cámara (encendido, apagado y lectura única).
- El componente `EscanerQR` aísla la librería: si se reemplaza, solo cambia ese archivo. Es reutilizable para el pase de lista.
- Licencia **MIT**.

### Negativas

- Si no hay lector nativo, el ponyfill descarga el binario `.wasm` de ZXing (~1 MB). **Por defecto lo descarga del CDN jsDelivr** (`fastly.jsdelivr.net/npm/zxing-wasm@.../`), así que en iOS/Firefox el primer escaneo requiere acceso a Internet. Después queda en la caché del navegador.
- `getUserMedia` solo funciona en **contexto seguro (HTTPS)**. En desarrollo se usa `@vitejs/plugin-basic-ssl` con `server.host: true`, y el celular debe aceptar el certificado autofirmado al entrar a `https://<IP-PC>:5173`.
- El bucle de cámara se mantiene a mano (sin componente de alto nivel).
- Se agrega una dependencia más al frontend que hay que mantener actualizada.
