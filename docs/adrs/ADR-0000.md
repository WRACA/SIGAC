# Decidir definitivamente la arquitectura del proyecto

**Status:** Aceptado

## Contexto

Durante el feedback dado por el profesor se cuestionó la selección del *tech stack* y la arquitectura planteada para el proyecto, por lo que ambas decisiones quedan nuevamente abiertas a discusión.

La propuesta preliminar definía una aplicación web construida principalmente con **Next.js, TypeScript, Prisma y PostgreSQL**, utilizando las capacidades de Next.js tanto para frontend como para parte de la lógica de backend.   

Aunque esta alternativa permite desarrollar rápidamente el MVP, concentra demasiadas responsabilidades dentro del mismo framework y dificulta establecer desde el inicio una separación explícita entre la interfaz de usuario y la lógica de negocio.    

SIGAC requiere actualmente una aplicación web responsiva para computadora, tablet y celular, incluyendo funcionalidades que dependen directamente del uso desde dispositivos móviles, principalmente el escaneo de códigos QR mediante cámara. Por esta razón, independientemente del framework seleccionado, el frontend deberá desarrollarse siguiendo una estrategia **mobile-first**.

Una aplicación móvil nativa se encuentra fuera del alcance actual del MVP. Sin embargo, existe la posibilidad de desarrollar una aplicación móvil independiente en el futuro. La arquitectura actual no deberá impedir esa evolución ni requerir reemplazar la lógica de negocio existente.

Por lo tanto, se considera necesario revisar nuevamente las tecnologías utilizadas y definir una arquitectura que permita:

- Separar frontend y backend desde el inicio.
- Mantener la lógica de negocio fuera del cliente.
- Exponer las funcionalidades del sistema mediante una API independiente.
- Desarrollar la interfaz web con enfoque mobile-first.
- Mantener PostgreSQL como almacenamiento relacional.
- Permitir que clientes futuros consuman el mismo backend.
- Mantener una complejidad adecuada para el alcance actual.
- Evitar introducir microservicios sin una necesidad funcional o de escalabilidad real.

---

## Decisión

Se debe replantear desde cero la selección de tecnologías utilizadas dentro del repositorio antes de continuar con el desarrollo de los módulos principales.

La nueva arquitectura deberá respetar la siguiente separación lógica:

```text
Frontend Web
     |
     | HTTPS
     | API
     v
Backend
     |
     v
PostgreSQL
```

Frontend y backend serán aplicaciones independientes, incluso si se mantienen dentro de un mismo repositorio.

La lógica correspondiente a autenticación, autorización, usuarios, membresías, actividades, inscripciones, sesiones, asistencias, pagos e indicadores deberá residir en el backend. El frontend será responsable principalmente de presentación, interacción con el usuario, manejo de estado de interfaz y comunicación con la API.

El backend deberá implementarse inicialmente como un **monolito modular**.

```text
sigac-api
├── auth
├── socios
├── instructores
├── actividades
├── horarios
├── inscripciones
├── sesiones
├── asistencias
├── membresias
├── pagos
└── dashboard
```

No se utilizará inicialmente una arquitectura de microservicios:

```text
auth-service
member-service
activity-service
attendance-service
payments-service
analytics-service
```

La elección definitiva de frameworks y lenguajes permanece pendiente y será discutida mediante un RFC independiente.

## Restricciones arquitectónicas

Las siguientes condiciones se consideran independientes de la selección concreta del *tech stack*.

| Aspecto | Decisión |
|---|---|
| Separación frontend/backend | Requerida |
| Comunicación | API sobre HTTPS |
| Formato principal de intercambio | JSON |
| Arquitectura backend | Monolito modular |
| Base de datos | PostgreSQL |
| Diseño frontend | Mobile-first |
| Web responsiva | Requerida |
| Aplicación móvil actual | Fuera del MVP |
| Compatibilidad con app móvil futura | Requerida |
| Lógica de negocio en frontend | Evitar |
| Validaciones de autorización | Backend |
| Microservicios | Fuera del alcance actual |

El sistema deberá mantener en servidor las validaciones relacionadas con permisos y reglas de negocio. Esto también coincide con el requisito existente de validar el acceso a los módulos desde el servidor y no únicamente desde la interfaz. :chatgpt-content-reference{index="3"}

## Combinaciones posibles

La separación entre cliente y servidor permite evaluar cada capa independientemente.

```text
Frontend
├── React / Next.js
├── Vue / Nuxt
├── SvelteKit
├── Angular
└── Flutter

Backend
├── FastAPI
├── Django REST Framework
├── Spring Boot
├── NestJS
├── Go
└── Rust / Axum
```

Por lo tanto, ninguna decisión de frontend obliga directamente a una tecnología backend específica.

Ejemplos:

```text
Next.js
   |
FastAPI
   |
PostgreSQL
```

```text
Nuxt
 |
Spring Boot
 |
PostgreSQL
```

```text

    |
    Go

```

```text

PostgreSQL
```

```text

   |
FastAPI
   |
PostgreSQL
```

La comparación detallada de estas combinaciones, sus ventajas, desventajas, riesgos y posibles pruebas de concepto deberá realizarse en el RFC asociado.

## Evolución futura

La arquitectura deberá soportar la incorporación posterior de un nuevo cliente sin modificar sustancialmente el backend.

```text
                    +----------------+
                    |   Frontend Web |
                    +--------+-------+
                             |
                             |
+--------------------+       |
| Aplicación móvil   |-------+
| futura             |       |
+--------------------+       |
                             v
                       +-----+-----+
                       | SIGAC API |
                       +-----+-----+
                             |
                             v
                       +-----+-----+
                       | PostgreSQL|
                       +-----------+
```

El frontend móvil podrá desarrollarse posteriormente utilizando Flutter, React Native, Kotlin, Swift u otra tecnología sin trasladar las reglas de negocio existentes.

## Consecuencias

### Positivas

- Frontend y backend podrán evolucionar independientemente.
- La lógica de negocio no dependerá de un framework frontend.
- Una futura aplicación móvil podrá reutilizar la API.
- La arquitectura facilita pruebas independientes por capa.
- Las reglas de autorización estarán centralizadas.
- Se mantiene una estructura suficientemente sencilla para el MVP.
- El backend podrá sustituirse o ampliarse con menor impacto en el cliente si los contratos de API se mantienen.
- Se evita adoptar microservicios antes de necesitarlos.

### Negativas

- Será necesario mantener como mínimo dos aplicaciones.
- El equipo deberá definir y mantener contratos entre frontend y backend.
- Será necesario resolver CORS, autenticación, manejo de sesiones/tokens y errores entre aplicaciones.
- Los despliegues de frontend y backend serán independientes.
- Dependiendo de la combinación elegida, el equipo podría trabajar con dos lenguajes y ecosistemas diferentes.
- La arquitectura presenta mayor configuración inicial que una solución completamente integrada con Next.js.
