# RFC-0000 — Selección del stack tecnológico para SIGAC

**Status:** Abierto a comentarios  
**Fecha de apertura:** 21/09/2026  
**Decisión relacionada:** [ADR-0000 — Decidir definitivamente la arquitectura del proyecto](../decisiones/ADR-0000.md)

## 1. Resumen

Este RFC tiene como objetivo discutir y seleccionar las tecnologías que serán utilizadas para implementar SIGAC.

La necesidad de realizar esta discusión surge de la decisión documentada en [ADR-0000](../decisiones/ADR-0000.md), donde se determinó replantear la arquitectura y el stack tecnológico del proyecto antes de continuar con el desarrollo.

Este documento no busca decidir nuevamente la arquitectura general. Las restricciones establecidas en el ADR se toman como punto de partida:

- frontend y backend separados desde el inicio;
- backend expuesto mediante una API independiente;
- PostgreSQL como base de datos;
- backend implementado inicialmente como un monolito modular;
- frontend desarrollado bajo un enfoque mobile-first;
- aplicación móvil fuera del MVP actual;
- posibilidad de incorporar clientes móviles en el futuro sin reemplazar el backend;
- microservicios fuera del alcance inicial.

El propósito de este RFC es determinar **qué tecnologías concretas utilizar dentro de esas restricciones**.

Para contexto adicional sobre el proyecto consultar:

- [Definición del proyecto](../../DEFINICION.md)
- [README del repositorio](../../README.md)
- [Confirmaciones del proyecto](../../confirmaciones.md)
- [ADR-0000](../decisiones/ADR-0000.md)

## 2. Motivación

La selección original del stack se realizó principalmente alrededor de Next.js, TypeScript, Prisma y PostgreSQL.

Después del feedback recibido se considera necesario evaluar nuevamente dicha selección, particularmente porque utilizar Next.js simultáneamente como frontend y backend no representa la separación arquitectónica que se busca mantener en SIGAC.

Además, la arquitectura debe contemplar dos escenarios con necesidades diferentes.

### Corto plazo

```text
Aplicación web
mobile-first
     |
     v
SIGAC API
     |
     v
PostgreSQL
```

El MVP deberá funcionar principalmente como aplicación web y deberá permitir:

```text
Administrador
├── gestión de socios
├── instructores
├── actividades
├── horarios
├── membresías
├── pagos
└── dashboard

Instructor
├── consultar clases
├── abrir sesión
├── escanear QR
├── registrar asistencia
└── consultar sesión

Socio
├── consultar actividades
├── inscribirse
├── mostrar QR
├── consultar membresía
└── consultar historial
```

### Largo plazo

Existe la posibilidad de desarrollar un cliente móvil independiente.

```text
                +-------------------+
                |    Frontend Web   |
                +---------+---------+
                          |
                          |
+----------------+        |
| App Android/iOS|--------+
+----------------+        |
                          v
                    +-----+-----+
                    | SIGAC API |
                    +-----+-----+
                          |
                          v
                    +-----+-----+
                    | PostgreSQL|
                    +-----------+
```

Por esta razón, la lógica de negocio no deberá depender de la implementación del frontend.

# 3. Alcance de este RFC

Este RFC debe producir decisiones sobre:

```text
[ ] Framework frontend

[ ] Lenguaje backend

[ ] Framework backend

[ ] Forma de acceso a PostgreSQL

[ ] Estrategia de migraciones

[ ] Contrato frontend/backend

[ ] Estrategia de autenticación

[ ] Estrategia general de testing

[ ] Organización técnica del repositorio
```

No corresponde a este RFC decidir:

```text
[x] Separación frontend/backend

[x] Uso de PostgreSQL

[x] Uso de monolito modular

[x] Mobile-first

[x] Implementación inmediata de aplicación móvil

[x] Implementación de microservicios
```

Estas cuestiones pertenecen al [ADR-0000](../decisiones/ADR-0000.md).

# 5. Arquitectura base

Todas las alternativas discutidas deberán poder implementarse aproximadamente bajo la siguiente estructura:

```text
                        CLIENTES

             +-------------------------+
             |     Frontend Web        |
             |      mobile-first       |
             +------------+------------+
                          |
                          | HTTPS
                          |
                          v
             +------------+------------+
             |        SIGAC API        |
             |                         |
             |    Monolito modular     |
             +------------+------------+
                          |
                          |
                          v
             +------------+------------+
             |       PostgreSQL        |
             +-------------------------+
```

Internamente el backend deberá poder separarse por dominio:

```text
sigac-api
├── auth
├── usuarios
├── socios
├── instructores
├── actividades
├── horarios
├── inscripciones
├── sesiones
├── asistencias
├── membresias
├── pagos
└── dashboard
```

No se propone:

```text
auth-service
member-service
activity-service
attendance-service
payments-service
analytics-service
```

## FE-01 — React + Next.js

| Lenguaje | TypeScript |
| Librería | React |
| Framework | Next.js |
| Estilos | Tailwind CSS |
| Componentes | shadcn/ui |
| QR | ZXing / html5-qrcode |
| Gráficas | Recharts |
| Testing | Vitest + Playwright |

### Ventajas y desventajas

| Ventajas | Desventajas |
|---|---|
| Ecosistema muy grande. | Next.js incluye numerosas funcionalidades de backend que probablemente no serían utilizadas. |
| Gran disponibilidad de componentes. | Puede existir tendencia a volver a acoplar frontend y backend. |
| Excelente para dashboards y CRUD. | Framework considerablemente grande para utilizarlo solamente como frontend. |
| Buen soporte TypeScript. | Requiere definir claramente qué responsabilidades pertenecen a la API. |
| Amplia documentación. | Una aplicación móvil futura utilizaría otro frontend. |
| Fácil implementación mobile-first. | Parte del valor de Next.js se pierde al tener backend separado. |

# 12. React + Vite vs Next.js

# 15. ORM vs SQL explícito

La selección del backend también determina cómo interactuar con PostgreSQL.

Existen tres aproximaciones principales:

```text
ORM

Django ORM
Hibernate
Prisma
SQLAlchemy ORM
```

```text
Query / data mapping

SQLAlchemy Core
Drizzle
SQLx
```

```text
SQL explícito

pgx
sqlc
SQLx queries
```

| Enfoque | Ventajas | Desventajas |
|---|---|---|
| ORM | CRUD rápido, relaciones sencillas | Oculta SQL, consultas complejas pueden degradarse |
| Query builder/data mapper | Equilibrio entre abstracción y control | Mayor código |
| SQL explícito | Máximo control y transparencia | Más trabajo manual |

SIGAC utiliza relaciones y restricciones importantes:

```text
Socio
  |
  +--> Membresía
  |
  +--> Inscripción
          |
          v
      Actividad
          |
          v
        Sesión
          |
          v
      Asistencia
```

Por lo tanto, cualquiera de las tres estrategias es viable siempre que permita mantener las restricciones en PostgreSQL.
